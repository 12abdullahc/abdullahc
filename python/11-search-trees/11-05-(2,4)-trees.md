## Background & Conceptual Intuition: Group Square Sizes

<span id="background-catalog"></span>

### 1. Reopen the seven-size tile catalog

The class still catalogs square tiles by **side length**. A side of `s` centimetres has one-tile area `s × s = s²` square centimetres. The value stored with key `s` is `(area of one tile, stock count)`. Start with one tile of each size:

| Side key | 2 cm | 4 cm | 6 cm | 8 cm | 10 cm | 12 cm | 14 cm |
| :------- | ---: | ---: | ---: | ---: | ----: | ----: | ----: |
| One-tile area | 4 cm² | 16 cm² | 36 cm² | 64 cm² | 100 cm² | 144 cm² | 196 cm² |

The seven one-tile areas total `4 + 16 + 36 + 64 + 100 + 144 + 196 = 560 cm²`. A lookup for side `12` returns `(144, 1)` because `12² = 144`.

Earlier guides stored these entries in a [binary search tree](11-01-binary-search-trees.md), then studied [AVL](11-03-avl-trees.md) and [splay](11-04-splay-trees.md) ways to reorganize it. Section 11.5 lets a node hold **several ordered entries**. Here is one valid arrangement of the same seven keys:

```text
                 [8]
               /     \
    [2 | 4 | 6]       [10 | 12 | 14]
```

The brackets group keys at a node; they do **not** describe a new tile or a stock count. All seven key-value entries remain present, so their areas still total 560 cm².

<span id="background-notation"></span>

### 2. Read brackets and empty endpoints

In each drawing, `[8]` holds one entry, while `[10 | 12 | 14]` holds three entries in increasing order. We show only their keys; each key carries its full `(area, stock)` value. An **internal node** holds entries. An **external node** is an empty endpoint where an unsuccessful search stops. It may be represented by `None` in code.

The two lowest boxes in the drawing each have **four conceptual external children**, one before the first key, one between each pair, and one after the last key. We omit those eight empty endpoints from most drawings. They are all two edges below the root:

```text
root [8] → internal box [2 | 4 | 6] or [10 | 12 | 14] → external endpoint
depth 0                 depth 1                                 depth 2
```

Call that common external depth `h = 2`. All examples below start from this seven-key tree unless a case explicitly resets to another valid grouping or a smaller tile subset.

## Part 1: 11.5 (2,4)-Trees

<span id="part-1-bridge"></span>

### 1. From binary branches to several choices

A binary search node has one key and chooses between two child intervals. A **multiway** search node can hold several ordered keys, creating several child intervals. For instance, a node `[10 | 12 | 14]` can direct a missing side length to one of four places.

A **(2,4) tree** is a multiway search tree whose internal nodes have two, three, or four children. It is also called a **2-3-4 tree**. The numbers name possible **child counts**: a 4-node has four children and **three** entries, not four entries.

<span id="part-1-goal"></span>

### 2. The organizing goal

A (2,4) tree keeps every empty external endpoint at the same depth. When insertion or deletion disturbs a node's allowed size, it repairs that node by a **split**, **transfer**, or **fusion**. This maintains a logarithmic worst-case search path as the catalog grows.

> **Mental model:** Keys inside one box divide a number line into intervals. Every route to an empty endpoint has the same number of levels, even when boxes hold different numbers of tile sizes.

## Part 2: 11.5.1 Multiway Search Trees

<span id="part-2-definition"></span>

### 1. Keys separate a node's children into intervals

A general multiway internal node with `d` children has `d − 1` sorted key-value entries:

```text
keys:       k₁ < k₂ < ... < k_(d−1)
children:  c₁  c₂  ...       c_d
```

Child `c_i` holds keys strictly between the neighboring separators `k_(i−1)` and `k_i`. At the ends, imagine `k₀ = −∞` and `k_d = +∞`. Equality with a stored separator means the search has found that entry.

For the right-hand tile box `[10 | 12 | 14]`, the four conceptual children divide side lengths this way:

| Child | Side-length interval | Example |
| :---- | :------------------- | :------ |
| `c₁` | Less than `10` | `9` would use this child. |
| `c₂` | Greater than `10` and less than `12` | `11` would use this child. |
| `c₃` | Greater than `12` and less than `14` | `13` would use this child. |
| `c₄` | Greater than `14` | `16` would use this child. |

At the root of our particular tree, this whole box lies to the **right** of key `8`, so its subtree contains only keys greater than `8`.

<span id="part-2-search"></span>

### 2. Follow one interval during a search

To find the area of a 12 cm tile, first compare `12` with root `[8]` and go right. In `[10 | 12 | 14]`, find the equal separator `12`. Its value gives `12² = 144 cm²`. The search visits **two internal nodes**; a node may require comparisons with more than one of its keys.

To seek an absent 11 cm tile, go right from `[8]`, then choose the interval between `10` and `12`. That child is external, so the lookup fails. It does not add the hypothetical `11² = 121 cm²` tile to the catalog.

The same route explains insertion later: searching for absent `16` reaches the external child **after** `14`. Its parent box is `[10 | 12 | 14]`.

<span id="part-2-external"></span>

### 3. Count external endpoints

**Proposition 11.7:** A multiway search tree with `n` stored entries has exactly `n + 1` external endpoints. Our seven-tile tree has `7 + 1 = 8`: four below each of its two bottom boxes.

Here is a short counting explanation. Let `I` be the number of internal nodes and `E` the number of external nodes. If internal node `w` has `d(w)` children, then it stores `d(w) − 1` entries. Every node except the root has one incoming link, so:

```text
sum of d(w) over internal nodes = I + E − 1

n = sum of (d(w) − 1)
  = (I + E − 1) − I
  = E − 1

therefore E = n + 1
```

For our drawing, `I = 3` and the child counts are `2, 4, 4`. Their sum is `10 = 3 + 8 − 1`, and the stored-entry count is `(2−1) + (4−1) + (4−1) = 7`. The book states this proposition and leaves its proof as an exercise.

<span id="part-2-representation"></span>

### 4. Represent the small search inside a node

The book suggests a linked general tree with a small **sorted map inside each internal node**. It calls this per-node map a **secondary** data structure: a simple sorted map helps implement the larger multiway search map. A separator key `k_i` can be associated with its value and the child immediately before it; the rightmost child is stored separately. A local `SortedTableMap.find_ge(k)` finds the first separator at least `k`:

| Local question at `[10 | 12 | 14]` | Local result | Next action |
| :-------------------------------- | :----------- | :---------- |
| Seek `12` | Equal separator `12` | Return `(144, 1)`. |
| Seek `11` | Next separator `12` | Follow the child before `12`. |
| Seek `16` | No separator at least `16` | Follow the rightmost child. |

For a general node with `d` children, searching its small sorted map costs `O(log d)`; across height `h` with maximum child count `d_max`, the search costs `O(h log d_max)`. A (2,4) node has at most three keys, so even a short unordered list or ordered array makes local searches and updates constant time. Section 11.5 gives this representation idea but does not supply a complete Python (2,4)-tree class.

## Part 3: 11.5.2 (2,4)-Tree Operations

<span id="part-3-rules"></span>

### 1. Two, three, or four children and one shared leaf depth

Every nonempty internal node has one of these legal sizes:

| Name | Children | Stored entries | Tile-key example |
| :--- | -------: | -------------: | :--------------- |
| **2-node** | 2 | 1 | `[8]` |
| **3-node** | 3 | 2 | `[8 | 14]` |
| **4-node** | 4 | 3 | `[2 | 4 | 6]` |

All external endpoints have the same depth `h`. In the seven-key starting tree, root `[8]` is a 2-node, both lower boxes are 4-nodes, and all eight external endpoints are at depth `2`. The empty tree consists only of an external root.

A node with **four entries and five children** is a temporary, overflowing **5-node**. A node with **zero entries and one child** is a temporary, underflowing **1-node**. The repair steps below remove these illegal states.

<span id="part-3-height"></span>

### 2. Why the height is logarithmic

Each internal node has between two and four children. If all external nodes are at depth `h`, there are at least `2^h` and at most `4^h` external nodes. Since Proposition 11.7 says there are `n + 1` of them, **Proposition 11.8** gives:

```text
2^h ≤ n + 1 ≤ 4^h

½ log₂(n + 1) ≤ h ≤ log₂(n + 1)
```

For the seven-size catalog, `n + 1 = 8` and `h = 2`. Indeed, `2² = 4 ≤ 8 ≤ 16 = 4²`, and the height bound reads `1.5 ≤ 2 ≤ 3`. The two-to-four child rule and the shared external depth force `h = O(log n)` as `n` grows.

A search visits at most one node per level and checks at most three keys there. Thus a (2,4)-tree search has **worst-case** `O(log n)` time for a nontrivial tree.

<span id="part-3-insert"></span>

### 3. Insert a key and split an overflowing node

Insertion first makes an unsuccessful search and reaches an external endpoint `z`. Put the new entry in sorted order in its parent `w`, and add one external child immediately to the left of `z`. This keeps the relationship **entries + 1 = children**. For an empty catalog, the first insertion creates a root 2-node with two external children.

From our starting tree, insert one 16 cm square, whose area is `16² = 256 cm²`. The search reaches the external child after `14`. Its full 4-node parent temporarily becomes:

```text
[10 | 12 | 14]  →  [10 | 12 | 14 | 16]
 legal 4-node       overflowing 5-node
```

The book splits four ordered entries by promoting the **third**, here `14`. The left box keeps `[10 | 12]`, the right box keeps `[16]`, and their external children stay in sorted interval order. Parent `[8]` receives `14`:

```text
                  [8 | 14]
                /     |     \
     [2 | 4 | 6]  [10 | 12]  [16]
```

The tree now has eight entries and nine external endpoints, all still at depth `2`. The one-tile area total is `560 + 256 = 816 cm²`. Moving `14` upward moves its full `(196, 1)` value with its key.

<span id="part-3-cascade"></span>

### 4. Let a split rise through the root

If the receiving parent already has three entries, promotion gives **that parent** four entries. Split it the same way. A split can continue upward until it reaches a parent with room.

If the **root** overflows, its split creates a new one-entry root. Every old external endpoint gains one level, so the common depth increases by exactly one. This is how the tree makes room while retaining its height rule.

For a concrete tile example, reset the seven keys to another valid grouping: root `[4 | 8 | 12]` with child boxes `[2]`, `[6]`, `[10]`, and `[14]`. Insert sides `16`, `18`, then `20`. The last insertion overflows `[14 | 16 | 18 | 20]`; promoting its third key `18` overflows the full root `[4 | 8 | 12 | 18]`. Promoting that root's third key `12` gives:

```text
                      [12]
                    /      \
              [4 | 8]      [18]
             /   |   \     /     \
           [2]  [6]  [10] [14 | 16] [20]
```

This independent example has ten entries and `11` external endpoints. Their common depth rose from `2` to `3`. The new tiles add `16² + 18² + 20² = 256 + 324 + 400 = 980 cm²`, so the one-tile total is `560 + 980 = 1540 cm²`.

<span id="part-3-delete"></span>

### 5. Delete an internal entry through its predecessor

A key in a bottom internal box can be removed there. If the requested key lies higher in the tree, exchange its **whole key-value entry** with its predecessor, the greatest entry in the child subtree immediately to its left. That predecessor is in a bottom box. Then physically remove the requested entry there and one corresponding external child.

Reset to the original tree and delete side `8` from the root. Its predecessor is side `6` in the left box `[2 | 4 | 6]`. Move `(6, (36, 1))` up and remove the old `8` entry from that bottom box:

```text
Before:                    After deleting 8:

       [8]                         [6]
      /   \                       /   \
[2 | 4 | 6] [10 | 12 | 14]   [2 | 4] [10 | 12 | 14]
```

The remaining bottom box `[2 | 4]` is a legal 3-node, so no underflow repair is needed. The catalog has six keys, seven external endpoints, and one-tile area `560 − 8² = 496 cm²`. Side `6` still maps to 36 cm²; key and value move together.

<span id="part-3-transfer"></span>

### 6. Repair underflow by transfer

If deleting a bottom box's only entry leaves a temporary 1-node, inspect an adjacent sibling. A **3-node or 4-node sibling** can give up one entry and one child. Move the parent's separating entry down into the underflowed node; move the sibling's nearest entry up to replace that separator. This is a **transfer**. The moved child keeps every external endpoint at the same depth.

Use the tree **after inserting 16** from Part 3. Its right box is `[16]`. Delete `16`, making that box empty. Its adjacent sibling `[10 | 12]` is a 3-node and can give up `12`. Move `12` to the parent and former parent separator `14` down to the right:

```text
Before deletion:               After deleting 16 and transferring:

       [8 | 14]                            [8 | 12]
      /    |    \                          /    |    \
[2 | 4 | 6] [10 | 12] [16]           [2 | 4 | 6] [10] [14]
```

The sibling's rightmost external child moves with the transfer. The remaining keys are again `2, 4, 6, 8, 10, 12, 14`. Their one-tile area returns from `816` to `816 − 256 = 560 cm²`, although their grouping differs from the starting tree.

<span id="part-3-fusion"></span>

### 7. Repair underflow by fusion

If **no adjacent sibling can lend** an entry, all available adjacent siblings are 2-nodes. Choose one and combine the empty node, the parent's separator, and that sibling into one legal node. This is a **fusion**. The parent loses one entry and one child; if it then underflows, repeat a repair higher in the tree.

For a small subset of the same square tiles, begin with root `[8]` and bottom boxes `[4]` and `[12]`. Delete `4`. Its box underflows, while sibling `[12]` has only one entry, so fuse that sibling with separator `8`:

```text
Before:                After deleting 4 and fusing:

       [8]                         [8 | 12]
      /   \                       /   |   \
    [4]  [12]              external endpoints
```

The old root has no entry left, so the fused box becomes the new root. The common external depth falls from `2` to `1`. The three-tile subset began with area `4² + 8² + 12² = 224 cm²`; the remaining two tiles total `8² + 12² = 208 cm²`. A fusion can likewise cascade through several ancestors before an empty root is removed.

<span id="part-3-costs"></span>

### 8. Account for the search and repair paths

Each node has at most three entries, so comparing or shifting entries locally takes constant time. Search follows one root-to-external path. Insertion may split nodes back up that path; deletion may transfer or fuse nodes back up it. No repair visits more than `O(h)` levels.

| Map action | Work in the (2,4) tree | Worst-case bound |
| :--------- | :--------------------- | :--------------- |
| Search for a side length | Follow one child interval at each level. | `O(log n)` |
| Insert a new side length | Search, then split upward if needed. | `O(log n)` |
| Delete a side length | Search, possibly find a predecessor, then repair underflow upward. | `O(log n)` |

These are bounds for **each operation**, not only for a sequence. Ordered queries such as `find_ge` also follow a logarithmic path; reporting `s` entries in a range takes `O(log n + s)` time. The book compares these bounds with the AVL sorted-map bounds. Updating the stock value at an existing key changes its value without adding or removing a child; for example, changing `6 → (36, 1)` to `6 → (36, 3)` leaves the tree's key grouping intact. The total **physical** area then becomes `560 + 2 × 36 = 632 cm²` in the original seven-size catalog.

## Part 4: Simple Geometry Study Cases

<details>
<summary><strong>Case Study 1: Find 12 cm and miss 11 cm</strong></summary>

**Scenario:** Use the original seven-key tree with root `[8]` and right box `[10 | 12 | 14]`.

**Problem:** A multiway node contains several possible separators, so the class needs the correct interval.

**Fix:** For `12`, go right at `8` and match key `12` in the next box. For `11`, go right at `8`, then follow the external interval between `10` and `12`.

**Result:** Side `12` returns `(144, 1)` because `12² = 144 cm²`. Side `11` is absent; no 121 cm² tile is added. All seven stored one-tile areas still total 560 cm².

</details>

<details>
<summary><strong>Case Study 2: Insert a 16 cm tile into a full box</strong></summary>

**Scenario:** Reset the original tree and add one tile with side `16`.

**Problem:** The right box `[10 | 12 | 14]` already holds the maximum three entries.

**Fix:** Temporarily form `[10 | 12 | 14 | 16]`, promote its third key `14`, and split the rest into `[10 | 12]` and `[16]`. Parent `[8]` becomes `[8 | 14]`.

**Result:** There are eight keys, nine external endpoints, and all endpoints remain at depth `2`. The new tile adds `16² = 256 cm²`, giving `560 + 256 = 816 cm²` of one-tile area.

</details>

<details>
<summary><strong>Case Study 3: A split reaches a full root</strong></summary>

**Scenario:** Reset the seven keys into valid root `[4 | 8 | 12]` with children `[2]`, `[6]`, `[10]`, `[14]`. Then add sides `16`, `18`, and `20`.

**Problem:** Inserting `20` overflows the rightmost child. Its promoted key also overflows the already-full root.

**Fix:** Promote `18` from `[14 | 16 | 18 | 20]`. Split the root `[4 | 8 | 12 | 18]` by promoting its third key `12` into a new root. Its children are `[4 | 8]` and `[18]`.

**Result:** All external endpoints now have depth `3` rather than `2`. Ten stored keys have `11` external endpoints. Their one-tile total is `560 + 256 + 324 + 400 = 1540 cm²`.

</details>

<details>
<summary><strong>Case Study 4: Delete an entry stored above the bottom level</strong></summary>

**Scenario:** Reset the original tree and remove the 8 cm square from root `[8]`.

**Problem:** Removing that root entry directly would leave its two child intervals without a separator.

**Fix:** Exchange the full `8 → (64, 1)` entry with predecessor `6 → (36, 1)` from left box `[2 | 4 | 6]`. Remove the old 8 cm entry there, leaving `[2 | 4]`.

**Result:** Root `[6]` separates `[2 | 4]` from `[10 | 12 | 14]`. No node underflows. Removing the 8 cm tile subtracts 64 cm², leaving `560 − 64 = 496 cm²` of one-tile area.

</details>

<details>
<summary><strong>Case Study 5: Transfer after deleting the new tile</strong></summary>

**Scenario:** Begin with the tree from Case Study 2: root `[8 | 14]`, children `[2 | 4 | 6]`, `[10 | 12]`, and `[16]`. Delete side `16`.

**Problem:** Removing the only entry from `[16]` makes a temporary underflowing 1-node.

**Fix:** The adjacent 3-node `[10 | 12]` lends `12` through the parent. The parent's `14` moves down to the empty right box, giving root `[8 | 12]` with children `[2 | 4 | 6]`, `[10]`, and `[14]`.

**Result:** The 16 cm tile's 256 cm² is gone, so the total returns to `816 − 256 = 560 cm²`. All eight external endpoints remain at depth `2`.

</details>

<details>
<summary><strong>Case Study 6: Fusion shortens a three-tile tree</strong></summary>

**Scenario:** Use only the existing tile sizes `4`, `8`, and `12` in root `[8]` with children `[4]` and `[12]`.

**Problem:** Deleting `4` empties its box, and sibling `[12]` is a 2-node with no entry to spare.

**Fix:** Fuse the empty box, parent separator `8`, and sibling `[12]`. The result `[8 | 12]` becomes the root.

**Result:** External depth falls from `2` to `1` while all remaining search intervals stay ordered. The area falls from `16 + 64 + 144 = 224 cm²` to `64 + 144 = 208 cm²`.

</details>

## Part 5: Summary

| Section 11.5 idea | Plain-language meaning | Square-tile example |
| :---------------- | :--------------------- | :------------------ |
| **Multiway node** | Several sorted entries create several child intervals. | `[10 | 12 | 14]` has four child intervals. |
| **External endpoint** | An empty child where a missing-key search stops. | The first seven tiles have eight external endpoints. |
| **(2,4) node sizes** | A legal node has two, three, or four children and one fewer entries. | `[8 | 14]` is a 3-node. |
| **Uniform external depth** | Every unsuccessful search reaches the same level. | The original catalog's endpoints all have depth `2`. |
| **Height bound** | With `n` entries, `2^h ≤ n+1 ≤ 4^h`. | Seven entries have `h = 2` in our starting tree. |
| **Overflow and split** | Promote the third of four temporary keys; keep two legal boxes. | Inserting `16` promotes `14`. |
| **Cascading split** | A full parent can split too; a new root adds one level. | Adding `16`, `18`, `20` to the full-root snapshot raises `h` to `3`. |
| **Internal-key deletion** | Move the predecessor entry, then remove it at the bottom. | Deleting `8` moves `6 → (36, 1)` to root. |
| **Transfer** | A sibling with spare entries lends through the parent. | Deleting `16` moves `12` up and `14` down. |
| **Fusion** | Merge with a minimal sibling and a parent separator. | Deleting `4` from the three-tile subset leaves root `[8 | 12]`. |
| **Operation cost** | Search and repair use at most a logarithmic path. | Search, insertion, and deletion each take worst-case `O(log n)` time. |
